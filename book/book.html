1장. 이 프레임워크는 무엇인가

seo-symfony는 다(多)테마 × 지역 SEO 사이트를 12개월에 걸쳐 구축·운영하기 위한 Symfony 기반 코드베이스다. 운영자는 페이지가 아니라 데이터만 만진다. URL · HTML · 사이트맵 · 리다이렉트는 모두 코드가 자동 생성한다.

해결하는 문제

"테마 × 지역" 매트릭스 키워드 사이트를 손으로 만들면 6개월쯤 충돌이 시작된다. 같은 키워드를 두 페이지가 노릴 때 서로의 순위를 깎아먹고 (카니발리제이션), 데이터 없는 빈 페이지가 사이트 전체 도메인 권위를 깎는다. 이 코드베이스는 그 충돌을 DB 트리거와 5개 엔티티로 사전 차단한다.

핵심 한 문장

사이트맵은 그리는 것이 아니라 데이터 모델로부터 결정론적으로 도출되는 것이다. 운영자는 5개 엔티티 중 3개만 만진다.

이 책이 다루는 것

  • 5개 엔티티 데이터 모델과 그 근거
  • 페이지·템플릿·CTA 시스템 사용법
  • 새 콘텐츠 타입·테마·로케일 추가
  • 운영자가 매일 보는 5개 사이트맵 뷰

2장. 5분 입양 — Quick Start

이 절차를 따르면 17개 데모 페이지가 뜨는 완성된 사이트를 받는다. 입양 후 세부 커스터마이즈는 4부에서 다룬다.

1. 환경 변수

cp .env .env.local
# .env.local에서 BRAND_*, DATABASE_URL 수정

2. DB 초기화 + 시드

php bin/console doctrine:database:drop --force --if-exists
php bin/console doctrine:database:create
php bin/console doctrine:migrations:migrate --no-interaction
php bin/console doctrine:fixtures:load --no-interaction
php bin/console app:admin:create me@example.com <password>
php bin/console app:seed:demo

3. 자산 빌드 + 서버

npm install && npm run build
php -S 127.0.0.1:8000 -t public

첫 입양 체크리스트

2부 아키텍처 이해

왜 이 5개 엔티티인가, 페이지는 어떻게 도출되는가,
발행 게이트는 왜 DB에서 강제하는가.

4장. 데이터 모델의 근거

이 시스템에는 정확히 5개 엔티티가 있고, 더 많지도 적지도 않다. 더 적으면 카니발리제이션을 막지 못하고, 더 많으면 운영자가 매일 결정해야 할 항목이 폭발한다.

왜 ContentNode가 따로 있는가

한 가지 흔한 오해: "Theme와 Region이 좌표축이라면 그 교차점은 그냥 SQL JOIN 아닌가?" 답은 아니다. 페이지에는 좌표 외에도 작성자, 본문 도입글, 5개의 verified 데이터, 발행 상태, KPI 스냅샷이 매달려야 한다. 이것을 놓을 곳이 ContentNode다.

왜 (theme, region) UNIQUE인가

이 한 줄의 제약(UNIQUE(theme_id, region_id))이 카니발리제이션을 DB 레벨에서 차단한다. 같은 좌표를 가리키는 두 페이지가 INSERT조차 되지 않는다. 어드민 UI나 API에서 검사하지 않는다 — 그곳들은 우회 가능하기 때문이다.

안 되는 모델
Theme, Region에 직접 본문/상태/저자 컬럼을 붙임 → 한 좌표가 여러 페이지를 만들거나, 빈 좌표가 페이지로 발행됨.
이 모델
좌표축(Theme/Region)은 분류만, 페이지 단위는 ContentNode 한 행, 재료는 DataPoint N행. 좌표가 있어도 ContentNode 행이 없으면 URL이 없다.
— 4 —

4장. 데이터 모델 — ERD 골격

5개 엔티티의 관계는 다음과 같다. Theme·Region은 자기 참조 트리, ContentNode는 두 트리의 교차점, DataPoint 는 노드에 매달린 재료, Redirect는 무덤 관리. 

THEME ─┐                       AUTHOR
       │self                       │
       └──> THEME                  │
                                   ▼
THEME ────────────> CONTENT_NODE ────── REGION
                          │                 │self
                          ▼                 └──> REGION
                     DATA_POINT

핵심 컬럼만

엔티티주요 컬럼제약
Theme slug, parent_id, depth depth ≤ 2
Region slug, parent_id, depth, admin_code depth ≤ 3
Author real_name, credentials, verified_at verified_at NULL이면 발행 차단
ContentNode theme_id, region_id, status, data_count, intro_text, body_template_id UNIQUE(theme_id, region_id)
DataPoint node_id, kind, value(JSONB), verified verified=true만 data_count에 반영
참고
kind는 5종: quantitative, qualitative, comparison, case, faq. 발행 게이트는 이 중 quant 1+, qual 3+, comparison 1+, 합계 5+를 요구한다.
— 5 —

5장. 페이지는 어떻게 도출되는가

URL은 손으로 만들지 않는다. (theme, region) 좌표를 받는 함수의 출력이다. 다음 의사코드 한 줄이 전체 URL 시스템이다. 

url(node) = "/" + theme_path(node.theme)
          + "/" + region_path(node.region) + "/"

경로 함수의 결과

theme.slug 경로region.slug 경로생성 URL
tutoring(NULL)/tutoring/
tutoringseoul/tutoring/seoul/
tutoringseoul/gangnam-gu/tutoring/seoul/gangnam-gu/
tutoringseoul/gangnam-gu/daechi-dong/tutoring/seoul/gangnam-gu/daechi-dong/
guides/how-to-choose-tutor(NULL)/guides/how-to-choose-tutor/

이 함수가 보장하는 5가지

  1. 같은 콘텐츠를 가리키는 두 URL이 존재할 수 없다 (canonical 자동 해결)
  2. 중복 URL이 INSERT 시점에 DB에서 거부된다
  3. URL 깊이 = 권위 단계, 부모가 자식의 prefix
  4. sitemap.xml이 SQL 한 줄 출력이다
  5. 운영자는 URL을 모르고도 데이터만 입력하면 된다
금지: 쿼리스트링 URL(?theme=...&region=...), 지역 우선 순서(/seoul/tutoring/), 깊이 5 이상.

5장. 4종 페이지 템플릿

페이지 템플릿은 단 4종이다. 1만 개 페이지가 있어도 4종으로 충분하다. 운영자는 템플릿을 고르지 않는다 — 코드가 theme.depth와 region.depth로부터 자동 결정한다.

4종 카탈로그

템플릿 ID적용 깊이핵심 차이
T_HUB0~1 (사이트 루트, 테마 허브)하위 트리 시각화 + 토픽 권위 강조
T_SIDO2 (시도)하위 시군구 매트릭스 + 광역 데이터
T_SIGUNGU3 (시군구)표준 10섹션, §5 비중 큼
T_DONG4 (동)표준 10섹션 + 인근 동 비교 강조

자동 결정 함수

template = decide_template(theme.depth, region.depth)
theme.depthregion.depth결과
0 (루트)NULLT_HUB
1 (테마 허브)NULLT_HUB
1~21 (시도)T_SIDO
1~22 (시군구)T_SIGUNGU
1~23 (동)T_DONG

이 함수가 결정론적이므로, 같은 좌표에는 항상 같은 템플릿이 적용된다. 운영자가 잘못 선택해서 사일로가 흐트러지는 일이 일어나지 않는다.

6장. 발행 게이트의 설계

Month 2~3에 운영자에게 가장 강하게 오는 유혹은 "오늘만 데이터 4개로 발행할까?"다. 그 한 번이 사이트 전체의 도메인 권위를 깎는다. 이 시스템은 그 결정을 운영자에게 맡기지 않는다 — DB 트리거가 거부한다.

canPublish(node) — 발행의 유일한 기준

function canPublish(node):
    if node.dataCount < 5:                  return false
    if not node.introText:                  return false
    if not node.author or
       not node.author.verified_at:         return false
    if node.region != null and
       node.parent.status != 'live':        return false
    if hasCanonicalCollision(node):         return false
    return true

왜 코드가 아니라 DB에서 강제하는가

방어선장점한계
UI 검증즉각 피드백API 직접 호출로 우회
API 레이어모든 클라이언트 보호SQL 콘솔로 우회
DB 트리거최종 방어선, 우회 불가지연된 피드백
비상 우회 기능은 처음부터 만들지 않는다. 비상 우회 버튼은 곧 일상 우회 버튼이 된다.
— 8 —

6장. 7개 무결성 트리거

DB가 코드를 거치지 않고도 무결성을 지키는 7개 트리거의 카탈로그. 이 중 하나라도 빠지면 Month 2~3 충돌 시기에 사이트가 무너진다.

트리거시점동작
fn_publish_gate BEFORE UPDATE content_node status='live'인데 게이트 미통과면 거부
fn_refresh_data_count AFTER ins/upd/del data_point 부모 data_count 재계산
fn_unique_theme_region BEFORE INSERT content_node 좌표 중복 거부
fn_parent_live_check BEFORE UPDATE content_node 부모 미발행이면 자식 live 거부
fn_dead_cascade_redirect AFTER UPDATE content_node dead 전이 시 Redirect 자동 생성
fn_region_depth_check BEFORE ins/upd region parent NULL인데 depth>0 거부
fn_theme_depth_check BEFORE ins/upd theme depth > 2 거부
팁
마이그레이션에 이 트리거들이 들어 있다. 입양 시 마이그레이션을 건너뛰지 말고 반드시 적용하라. 트리거 없는 DB는 이 프레임워크가 아니다.

7장. 5가지 게이트 경로

모든 BodyTemplate은 다음 5개 게이트 경로 중 하나를 사용한다. 게이트 경로는 "이 페이지를 발행하려면 어떤 데이터가 얼마나 필요한가"를 정의한다.

경로요구 데이터적용 BodyTemplate
matrix quant ≥ 1, qual ≥ 3, comparison ≥ 1, 합계 ≥ 5 matrix_default, matrix_compact
guide qual ≥ 4, faq ≥ 3, intro_text 필수 guide_*, faq_focus
essay 본문 길이 ≥ 1500자, intro_text 필수 essay
report quant ≥ 5 또는 comparison ≥ 3 report_quant, report_compare
case_study case ≥ 1 (verified), 출처 필수 case_study

핵심 원칙

게이트 경로는 단순히 "5개 이상"이 아니라 5개 이상이면서 그 구성이 §3·§4·§5(정량·정성·비교)를 모두 포함해야 한다. 이 합이 자연스럽게 5를 넘게 설계되어 있다.

게이트 경로 변경은 7단계의 첫 번째 결정이다. 새 콘텐츠 타입을 추가할 때 먼저 어느 경로를 쓸지 정하고 시작한다 (11장 참고).

8장. 페이지 시스템

URL 하나가 어떻게 한 페이지로 변환되는지의 전체 파이프라인. 어디를 만질지 정하기 전에 이 흐름을 이해해야 한다.

4가지 페이지 유형

유형URL 패턴좌표 조건
루트/없음 (PublicHomeController)
테마 허브/{theme}/region IS NULL AND theme.parent IS NULL
지역 페이지/{theme}/{sido}/.../region IS NOT NULL
자식 테마/{parent}/{child}/region IS NULL AND theme.parent IS NOT NULL

좌표 → 노드 매핑

PublicNodeController는 모든 비-루트 URL을 받고, PathResolver로 좌표(theme + region)를 ContentNode 행에 매핑한다. 매칭 실패 시 404, status='dead'이면 Redirect 테이블 조회 후 301.

템플릿 컨텍스트

PublicNodeController::buildContext()가 모든 템플릿에 주입하는 변수: node, url, h1, template(BodyTemplate enum), body_html, byKind(DataPoint를 kind별 그룹화, verified만), parent·siblings·children, theme_children·theme_siblings, urls(UrlBuilder), crumbs, json_ld·breadcrumbs_jsonld.

8장. 디스패처 우선순위

node.html.twig는 분기 로직만 담는 디스패처다. 어떤 템플릿으로 렌더할지 다음 우선순위로 결정한다. 첫 매칭에서 멈춘다 — 위가 아래를 이긴다.

매칭 순서

1. template_override 파일 존재?  → 사용 (이하 무시)
   templates/public/hubs/{theme-path}.html.twig
   조건: region IS NULL (지역 페이지는 절대 오버라이드 불가)

2. body_template == guide_*?     → _guide.html.twig
3. body_template == essay?       → _essay.html.twig
4. body_template == report?      → _report.html.twig
5. body_template == case_study?  → _case_study.html.twig

6. 그 외 (지역 페이지 + 오버라이드 없는 매트릭스 허브)
   → matrix_template
     = templates/public/matrix/{root-theme-slug}.html.twig
       (없으면 _matrix.html.twig 제네릭 fallback)

캐시 헤더

Cache-Control: public, max-age=300, s-maxage=1800
Last-Modified: {node.last_review_at or first_published_at}

브라우저 5분 / CDN 30분. If-Modified-Since로 304 가능. 무효화 트리거는 last_review_at 변경.

이 우선순위는 외워두거나 자주 참조할 가치가 있다. 이것이 시스템 전체의 외형 통제 규칙이다.

10장. CTA 시스템 — 핵심 모델

CTA(Call To Action)는 페이지마다 박힌 행동 유도 블록이다. 사이트 전반의 CTA를 YAML 설정 한 파일(config/cta.yaml)에서 결정하고, 페이지 위치(슬롯)와 콘텐츠 타입(BodyTemplate) 조합으로 분기한다.

5개 엔티티 외부

CTA는 Theme/Region/Author/ContentNode/DataPoint 어디에도 속하지 않는다. 브랜드 식별값과 사업 정책의 결합으로 보고 데이터 모델 밖에 배치됐다. 운영자는 CTA를 만지지 않으며, 폼 제출도 자체 DB에 저장하지 않는다 — 외부 채널로 forward.

핵심 모델: 슬롯 × BodyTemplate → CTA 객체

개념의미위치
슬롯 (CtaSlot)페이지 안 위치navbar / hero / final
타입 (CtaType)행동 종류phone / form / external / email / messenger
CTA 객체한 슬롯에 채워지는 단위label, payload, hint, assurances

매핑 규칙

  1. 페이지 진입 → 슬롯 + 페이지의 BodyTemplate이 CtaResolver에 입력
  2. slots.<slot>의 룰들을 위에서 아래로 평가
  3. match는 fnmatch 패턴 — 'guide_*', 'essay', '*'
  4. 첫 매칭의 cta 키로 ctas.<key> 조회
  5. 매칭 실패 시 brand_phone 안전 디폴트

10장. 폼 + Notifier

type: form인 CTA는 payload.form 키로 FormType을 식별한다. 현재 등록된 폼: consult → ConsultFormType (name, phone, region, memo, agree + honeypot, CSRF).

제출 흐름

사용자 폼 제출
    ↓
POST /cta/submit/{form}              ← CtaSubmitController
    ↓
honeypot + CSRF + validation
    ↓
CompositeCtaNotifier.send(form, data)  ← 텔레그램 + 디스코드 fan-out
    ↓
GET /cta/thank-you (X-Robots-Tag: noindex)

새 폼 추가하기

  1. src/Form/Cta/<Name>FormType.php 생성
  2. config/cta.yaml의 ctas:에 항목 추가
  3. config/services.yaml에 form 서비스 등록
  4. Notifier가 새 폼을 처리하도록 분기 추가 (또는 generic으로 처리)

새 Notifier 추가

CtaNotifierInterface를 구현하고 composite_cta_notifier에 태깅. Slack, 이메일, CRM API 등 자유롭게 fan-out 가능.

폼 데이터는 자체 DB에 저장하지 않는다. 정책이 바뀌면 Notifier 추가만 하면 되고, 데이터 모델은 변하지 않는다.

11장. 새 콘텐츠 타입 추가하기 — 7단계

가벼운 대안: enum 안 만지기

새 콘텐츠 타입이 시각적으로 비슷하면 enum을 안 늘리고 자식 테마 + 기존 변종으로 해결할 수 있다. enum 추가가 정당한 경우는 셋 중 하나라도 참일 때: 발행 게이트 임계값이 다름, 시각 시그니처가 명확히 다름, 기존 변종으로 표현 불가능. 셋 다 거짓이면 기존 변종을 쓴다.

순서 주의
게이트 변경 시: 함수를 먼저 교체 → row 업데이트 나중. 옛 트리거가 새 값을 잘못 분류해 강등시키는 함정을 피한다.

12장. 테마와 콘텐츠 운영

새 테마 추가하기

대시보드 /admin/themes/new에서 추가. 자식 테마는 parent 드롭다운에서 부모 선택 → depth는 자동 계산. URL /{parent}/{child}/로 자동 생성.

사전 질문 3개

새 테마 추가 전에 자문하라:

  • 자체 데이터를 쌓을 수 있는 영역인가?
  • 기존 테마와 키워드 분리되는가?
  • 최소 5개 노드를 발행할 수 있는가?

셋 다 ✓이면 진행. 그렇지 않으면 자식 테마로 충분한지 검토. 깊이 제약은 Theme.depth ≤ 2 — 사일로 흩어짐 방지를 위한 의도된 제한이다.

운영 워크플로우 (CRUD)

엔티티URL prefix비고
Theme/admin/themesparent 선택 → depth 자동
Region/admin/regions행정구역 트리
Author/admin/authorsverified는 별도 verify 액션
ContentNode/admin/nodesBodyTemplate 드롭다운
DataPoint/admin/nodes/{id}/datapoints노드 안에서 추가

게이트 통과 못 할 때

에러 메시지가 정확한 작업 항목이다: data_count >= 5, non-empty intro_text, verified author required, parent live check fail, verified FAQ data points >= 3. 게이트는 우회 안 된다.

16장. 운영자가 보는 5개 뷰

사이트맵은 하나의 트리가 아니라 같은 데이터의 5개 뷰다. 각 뷰는 다른 결정에 쓰인다. 입양 개발자가 어드민이 무엇을 다루는지 알아야 페이지·CTA 결정을 잘 할 수 있다.

1. 발행 트리 뷰 (Public Tree)

사용자와 검색엔진이 보는 것. sitemap.xml과 사이트 내비게이션의 원천. status='live'인 노드만 포함. 4단계 깊이가 최대치 (사이트 → 테마 → 시도 → 시군구 → 동).

2. 데이터 매트릭스 뷰 (Data Matrix)

운영자가 매일 보는 화면. 어느 칸을 채워야 하는지 한눈에 보인다. ✓ live (data ≥ 5) / ◐ noindex (1~4) / ✗ dead (0).

과외학원학습
강남구✓ 9✓ 12✓ 15
서초구✓ 7✓ 5✓ 8
송파구✓ 6◐ 4◐ 2
군포시✓ 8◐ 3◐ 1
금정구◐ 2✓ 5✗ 0

가장 효율적인 작업 패턴: ◐ → ✓. 게재 의도는 검증됐고 데이터만 부족한 칸 — 데이터 1~2개 추가로 발행 가능.

16장. KPI 히트맵 + 사일로 무결성

4. 사일로 무결성 뷰 (Silo Integrity)

구조 점검용. 자동 검사기가 다음을 검출:

  • 부모 없는 노드 (고아)
  • 다른 테마로의 직접 링크 (사일로 침범)
  • 끊긴 내부 링크
  • 부모의 자식 목록에서 누락된 자식
  • depth가 부모와 정합되지 않는 노드

매주 자동 실행, 위반 시 알림. /admin/silo에서 즉시 확인 가능.

사일로 침범은 가장 흔한 사고다. 다른 테마 페이지로의 직접 링크는 반드시 부모 허브로 우회시켜야 한다.

16장. 갱신 큐 + 일일 루틴

5. 갱신 큐 뷰 (Refresh Queue)

운영자의 매일 작업 목록. 자동 우선순위가 매겨진다.

우선순위트리거 조건
190일 미갱신 (last_review_at 기준)
2새 verified DataPoint 있는데 페이지 미반영
3Search Console 노출 +50% 급증
490일 트래픽 0인 live 노드

일일 루틴 (15~30분)

  1. 갱신 큐 확인 (5분) — 우선순위 1·2 처리
  2. 매트릭스 빈칸 채우기 (10~20분) — ◐ 칸 1개 이상 ✓로 승급 시도
  3. 이전 추가된 DataPoint 검증 — verified=true 토글
  4. SC 알림 점검
  5. 사일로 검사기 결과 확인 — 위반 즉시 처리

분기 점검 (매 분기 마지막 주)

  • KPI 히트맵에서 트래픽 0 페이지 추출
  • 카니발리제이션 검출기 결과 검토 → 통합 결정
  • 90일 미갱신 일괄 검토
  • 다음 분기 발행 캘린더 락

콘텐츠 타입 / 게이트

질문답

질문답

부록 C. 운영자 치트시트

일일 (15~30분)

  • 갱신 큐 확인 → /admin/queue → 우선순위 1·2 처리
  • 매트릭스 빈칸 채우기 → /admin/matrix → ◐ 1+를 ✓로
  • 이전 추가 DataPoint 검증 → verified=true 토글
  • SC 알림 점검
  • 사일로 검사기 결과 → /admin/silo → 위반 즉시 처리

주간 (1시간)

  • draft → live 후보 검토
  • 사일로 검사 결과 처리
  • Search Console 알림 정리

분기 (반나절, 매 분기 마지막 주)

  • KPI 히트맵에서 트래픽 0 페이지 추출 → 보강/통합/삭제 결정
  • 카니발리제이션 검출기 결과 검토 → 통합 결정
  • 90일 미갱신 일괄 검토
  • 새 테마/지역 후보 검토 (자동 데이터 추가)
  • 다음 분기 발행 캘린더 락 (lock)
  • 분기 동안 변경된 status 이력 리뷰

발행 전 페이지 체크 (요약)

  • verified DataPoint ≥ 5 (정량 1+, 정성 3+, 비교 1+)
  • intro_text 작성 (2~3문장)
  • author.verified_at NOT NULL
  • parent.status = 'live'
  • 인접 지역 링크 ≥ 3 (사일로 안)
  • 다른 테마로의 직접 링크 0
  • 모바일 LCP < 2.5초
